## In one minute

Everything sed.i remembers lives in one PostgreSQL database with the pgvector extension. There are 19 application tables. Almost every one hangs off `users`, and every row a user owns carries that user's id, because the application filters by it in every query. A saved URL becomes one row in `content_items`; background jobs then add rows in `content_chunks`, `entities`, `entity_mentions`, `entity_relations` and `tag_embeddings` around it.

Deleting an article only sets a timestamp (`deleted_at`). That is a soft delete: the row stays for seven days and a daily job removes it for good. Most queries filter soft-deleted rows out, but a few paths do not, and this chapter lists them. Indexes do three jobs: a partial unique index stops the same URL being saved twice, a GIN index serves keyword search, and HNSW indexes serve vector search. The schema changes only through Alembic migrations, which Railway runs before each deploy.

## The problem

**What does the database hold, and what rules does the schema itself enforce, as opposed to the rules the application code is trusted to follow?**

The obvious simpler design is to keep a user's library as JSON files or one document per user. It works for one user and falls apart when the app needs to ask questions across rows: "unread articles tagged coffee", "the 10 passages closest to this question", "who mentioned this entity in how many articles". A relational database answers those with indexes instead of reading everything. It also gives guarantees that application code alone cannot: two requests that save the same URL at the same moment cannot both succeed if the database refuses the second, and deleting a user cannot leave orphaned passages behind if the database cascades the delete.

The cost is that a schema is a contract that changes slowly. Changing it on a live database needs a controlled process (migrations), and some rules (who may see which row) are not expressible in the schema here at all. They live in application code, which is the weakest part of the design and is discussed under "What is weak or missing".

## Mental model

Think of a filing room with one cabinet per person. `users` is the directory of cabinets. Inside a cabinet each article is a folder (`content_items`). Clipped to a folder are sticky notes (`highlights`), index cards for each passage (`content_chunks`), and slips naming the people and ideas mentioned in it (`entity_mentions`). A separate card catalog of those people and ideas (`entities`) is kept per cabinet. One shelf, `tag_embeddings`, is shared by everyone.

The precise terms:

| Term | Meaning here |
|---|---|
| Primary key (PK) | The column that identifies a row. Here it is a UUID (a 128-bit random id) generated by Python (`default=uuid.uuid4`), not by the database. |
| Foreign key (FK) | A column that must match a row in another table. `ON DELETE CASCADE` means deleting the parent deletes the child rows. |
| Soft delete | Marking a row deleted (`deleted_at` set) instead of removing it. |
| JSONB | A column holding a JSON document, stored in a binary form Postgres can index and query. |
| ARRAY | A column holding a list of values of one type, such as `text[]`. |
| pgvector `vector(1536)` | A column holding 1,536 floating-point numbers; see [Chunking and embedding](/retrieval/chunking-and-embedding/). |
| tsvector | A pre-processed form of text (stemmed words with positions and weights) that full-text search matches against. |
| Partial index | An index that covers only the rows matching a `WHERE` clause. |
| Migration | A numbered script that moves the schema from one version to the next. |

## Walkthrough: one saved URL, row by row

The input is a URL a user pastes: `HTTPS://Example.COM/Coffee/Espresso/?utm_source=news&b=2&a=1#intro`. This walkthrough was run against a scratch database: a new database on the local Postgres, built by running every real migration (`alembic upgrade heads`, then `scripts/post_deploy.py`) and filled with the application's own functions. Three things are stand-ins, because a real run needs OpenAI: the article text is a few sentences of my own, the embeddings are random unit vectors (illustrative values, real shape), and the entity is created by calling `upsert_entity` directly instead of through an LLM call. What the database does with the rows is captured output.

### Step 0: build the schema

Notice that migration `f4c8b6e21a3d` is about HNSW indexes, yet it does nothing in `upgrade()`: the indexes are built afterwards by `post_deploy.py`. The reason is explained under "Migrations".

### Step 1: the user pastes the URL (`content_items`, one row)

`ingest_url` normalizes the URL, looks for an active duplicate, and inserts a row with `processing_status = 'pending'`. Then the API returns 201 and queues extraction.

```text
raw       : HTTPS://Example.COM/Coffee/Espresso/?utm_source=news&b=2&a=1#intro
normalized: https://example.com/Coffee/Espresso?a=1&b=2
```

Scheme and host are lowercased, the trailing slash and the fragment are dropped, the tracking parameter is removed and the remaining parameters are sorted. The path keeps its case, because paths are case-sensitive on many servers. Saving the same page again with `fbclid=zzz` added is refused:

```text
step1b duplicate rejected: DuplicateContentError
```

At this point the row has no title, no embedding and no text. Its `search_vector` is already not null: the trigger fires on insert and stores an empty vector. That is harmless but worth knowing: `search_vector IS NOT NULL` does not mean "searchable".

### Step 2: extraction fills the row (`content_items`, same row)

Extraction updates the same row: title, author, `full_text`, word count, tags, `processing_status = 'completed'`. Each of those updates fires the `tsvector_update` trigger, which rebuilds `search_vector` inside Postgres, so application code never computes it. After setting a title, an author and a one-sentence body, the vector looked like this (captured, shortened):

```text
'a':11A 'barista':10A,12A 'coffe':13B,20C 'coffee':14B,29C 'espresso':2A,6A,15C,24C
'extract':3A 'extraction':7A 'forc':16C 'forces':25C 'grind':21C,3...
```

Each word has positions and a weight letter: A for title and author, B for description and tags, C for the body. Words appear twice, as a stemmed form from the `english` dictionary (`coffe`, `forc`) and as written from the `simple` dictionary (`coffee`, `forces`). A query for `espressos` matched this row (captured: `fts match 'espressos': 1`) because the English dictionary stems both to `espresso`.

### Step 3: the article-level embedding (`content_items.embedding`)

`generate_embedding` writes one 1,536-number vector into the same row. No new row, just a filled column (captured: `embedding dims: 1536`). The same task then queues two more: chunking and article analysis.

### Step 4: chunks (`content_chunks`, n rows)

`split_article_into_chunks` cuts the text; each chunk becomes a row with the item id, the user id, its position and its own vector.

```text
step4 chunks: [(0, 91, 1536), (1, 2660, 1536), (2, 1772, 1536)]
```

The tuples are (chunk_index, characters, vector dimensions). The sample article was a short intro plus one long section of repeated sentences, so it split into three chunks.

### Step 5: entities and tags (`entities`, `entity_mentions`, `tag_embeddings`)

Article analysis (one LLM call) returns tags and named entities. The tags are embedded and stored in `tag_embeddings`, one row per distinct label across all users. Each entity goes into `entities` (one row per user and lower-cased name), and one `entity_mentions` row links it to this article. Relations between entities would go in `entity_relations`. The scratch run created one tag, one entity and one mention. Asking for "Espresso" and then "espresso" returned the same entity:

```text
step5 same entity for different case: True
row counts {'users': 1, 'content_items': 1, 'content_chunks': 3, 'entities': 1, 'entity_mentions': 1, 'tag_embeddings': 1}
```

The case-insensitive match is enforced by the unique index `uq_entity_user_lower_name` on `(user_id, lower(name))`, not only by the code that looks before inserting.

### Step 6: delete, re-save, and the unique index

Soft-deleting the item sets `deleted_at`. Because the unique index only covers rows where `deleted_at IS NULL`, saving the same URL again is allowed and creates a second row:

```text
step6 re-save after soft delete ok; items for url: (2, 1)
```

The tuple is (rows for the user, active rows). Then a raw `INSERT` of a second active row for the same user and URL, which bypasses the application's duplicate check, is refused by the database itself:

```text
step6b db rejects: duplicate key value violates unique constraint "uq_content_items_user_url_active"
```

Finally, hard-deleting the first item removed its children through the foreign keys, but not the entity:

```text
after hard delete chunks/mentions: (0, 0, 1)
```

The tuple is (chunks, mentions, entities). The chunks and the mention are gone; the `entities` row remains, because the entity belongs to the user, not to one article. Nothing in the code decrements `article_count` or removes entities that no article mentions any more (inferred from the code: no such statement exists in `app/`).

## What the dev database looks like

Measured on the development database with `pg_class`, `pg_indexes` and `pg_relation_size` (one person's library, aggregates only; the database is 283 MB):

| Table | Rows | Total size (data, TOAST, indexes) |
|---|---|---|
| `content_items` | 369 (71 active, 298 soft-deleted) | 123 MB |
| `tag_embeddings` | 6,626 | 115 MB |
| `entities` | 954 | 14 MB |
| `content_chunks` | 573 | 10 MB |
| `research_runs` | 131 | 5.7 MB |
| `highlights` | 77 | 2.0 MB |
| `entity_relations` | 275 | 1.9 MB |
| `entity_mentions` | 1,393 | 0.9 MB |

Two things stand out. `content_items` holds 123 MB for 369 rows, but the row heap itself is 720 kB: the rest is TOAST (Postgres's side storage for large values), mostly `full_text`, which sums to 93 MB for 318 rows that have text. And `tag_embeddings` is the second largest table because every distinct label is stored with a 6 KB vector, and 57 MB of its 115 MB is its IVFFlat index.

The vector and text indexes, from `pg_indexes` and `pg_relation_size` on the same database:

| Index | Type and definition | Size |
|---|---|---|
| `content_chunks_embedding_hnsw` | HNSW, `vector_cosine_ops`, m=16, ef_construction=64 | 4,568 kB |
| `entities_embedding_hnsw` | HNSW, same parameters | 6,656 kB |
| `content_items_embedding_hnsw` | HNSW, same parameters (295 vectors) | 1,568 kB |
| `highlights_embedding_hnsw` | HNSW, same parameters | 616 kB |
| `idx_content_items_search_vector` | GIN on `search_vector` | 6,296 kB |
| `idx_highlights_search_vector` | GIN on `search_vector` | 96 kB |
| `tag_embeddings_embedding_idx` | IVFFlat, `vector_cosine_ops`, lists=100 | 57 MB |
| `ix_research_memory_embedding` | IVFFlat, lists=100 | 1,608 kB |
| `uq_content_items_user_url_active` | btree unique on `(user_id, original_url)` where `deleted_at IS NULL` | 16 kB |

The chunk table is 10 MB in total and its HNSW index is 4.5 MB, so the index is nearly half the table's size. As noted in chapter 2.2, the main semantic search query computes exact distances and does not use that index.

### JSONB and ARRAY columns

JSONB is used where the shape varies or is read as a whole: `content_items.vertical_metadata`, `users.reading_patterns`, `vinyl_records.tracklist` and `videos`, `user_memory_events.metadata`, and seven columns on `research_runs` (`sub_questions`, `subagent_results`, `item_ids_retrieved`, `searches_run`, `result`, `error`, `budget`). ARRAY is used for flat lists: `content_items.tags` and `auto_tags`, the vinyl `genres`, `styles` and `tags`, `reading_clusters.article_ids` and `tag_labels`, `research_memory.source_item_ids`. Neither JSONB nor the ARRAY columns have a GIN index in this database, so "all items with tag X" is a scan filtered by `user_id`, which is cheap at this size (measured: `content_items` has 13 indexes, none on `tags`). The array of ids in `reading_clusters.article_ids` has no foreign key, so a hard-deleted article can leave a stale id in a cluster until the clustering task rewrites it (inferred from the schema).

### Soft delete: where it is honoured

`DELETE /content/{id}` sets `deleted_at`. The daily beat task `cleanup-old-deleted-items` hard-deletes rows whose `deleted_at` is more than 7 days old; the foreign keys then remove chunks, highlights, mentions and relations.

<!--src content-queue-backend/app/tasks/cleanup.py-->
```python
cutoff_date = datetime.utcnow() - timedelta(days=7)
```

Counting by reading the code (every `deleted_at` filter under `app/`):

| Path | Honours `deleted_at` |
|---|---|
| REST content, lists, analytics, search (`api/content.py`, `api/lists.py`, `api/analytics.py`, `api/search.py`) | Yes |
| Hybrid search, router, chunk sweep, clustering, memory, tagging | Yes |
| Public routes (`api/endpoints/public.py`) | Yes, for items and for vinyl; profile lookup has no soft delete to check |
| MCP tools for content, lists, highlights, stats; `synthesize_topic` through `hybrid_search` | Yes |
| MCP `query_library` (text to SQL) | **No.** The schema the model sees lists no `deleted_at` column and the validator never requires one, so generated SQL can return trashed items and their chunks |
| Highlight endpoints (`api/highlights.py`) | **No.** They look the item up by id and user only, so a trashed item still accepts and lists highlights |
| Entity graph (`core/entity_graph.py`) | **No.** It reads mentions and entities and never joins `content_items`, so mentions from a trashed article count until the hard delete |

The `query_library` gap is open in the current code (checked by reading `mcp/tools/query.py`: the string `deleted_at` does not appear). The fix is to add a `deleted_at IS NULL` requirement to the generated-SQL guidance and enforce it in the validator, or to expose a filtered view instead of the base table.

### The partial unique index and URL normalization

<!--src content-queue-backend/alembic/versions/5534fbac2811_add_unique_constraint_content_url.py-->
```python
op.execute(
    """
    CREATE UNIQUE INDEX uq_content_items_user_url_active
    ON content_items (user_id, original_url)
    WHERE deleted_at IS NULL
    """
)
```

This index has two jobs: it is the final guard against duplicate saves, and it makes the lookup in `find_existing_active_item` a single indexed read. The second job only works if every stored URL is already normalized. Migration `a7d3e9c15b42` made that true for old rows. It reads every active item, computes the normalized form with a frozen copy of `normalize_url` (a migration must not change behaviour when the application function is edited later), and rewrites the URL in place. If two active rows of one user normalize to the same URL, it keeps one (the one with highlights, else the already-normalized one, else the newest), soft-deletes the others, and copies their list memberships to the winner. It takes `LOCK TABLE content_items IN SHARE ROW EXCLUSIVE MODE` first so that no concurrent insert can collide with a rewrite. It cannot be reversed: the original spellings are not kept. On the empty scratch database it scanned zero rows; it has not been run against production in this guide.

The earlier migration that created the index (`5534fbac2811`) removed duplicates with a hard `DELETE`, keeping the newest. The later one soft-deletes instead, so nothing is lost.

### Triggers and full-text search

Keyword search needs a tsvector built from several columns. Postgres cannot use a generated column here (the migration notes that `to_tsvector` is only STABLE, and generated columns require IMMUTABLE expressions), so a trigger recomputes it. This is the current definition, taken from the migration that added the body text:

<!--src content-queue-backend/alembic/versions/e3f7a2c9b1d4_add_full_text_to_search_vector.py-->
```sql
CREATE TRIGGER tsvector_update
BEFORE INSERT OR UPDATE OF title, author, description, tags, full_text
ON content_items
FOR EACH ROW EXECUTE FUNCTION content_items_search_vector_update();
```

`UPDATE OF` lists the columns: changing `is_read` does not fire it, changing `full_text` does. The function body is in the same file; it concatenates the `english` and `simple` vectors of each column with weights A, B and C, as shown in step 2. Highlights have a second trigger, `highlights_tsvector_update`, over `text` and `note`. The cost is that every update to `full_text` recomputes the vector for the whole article inside the transaction. The GIN index on it is 6.3 MB for 369 rows.

### Alembic and the deploy path

Alembic keeps its version in a one-row table, `alembic_version`. Each migration file names its parent with `down_revision`. There are 49 files and history has merge revisions (for example `013_merge_heads.py` and `9377e6bfc72e_merge_heads_entities_analyzed_at_and_.py`), because two branches each added a migration. Alembic refuses ambiguity, so CI counts heads and fails the build if there is more than one:

<!--src .github/workflows/backend-ci.yml-->
```yaml
HEAD_COUNT=$(poetry run alembic heads 2>/dev/null | grep -c "(head)" || true)
if [ "$HEAD_COUNT" -ne 1 ]; then
```

On Railway, `railway.json` runs migrations in a pre-deploy step, before the new version receives traffic:

<!--src content-queue-backend/railway.json-->
```json
"preDeployCommand": ". /opt/venv/bin/activate && poetry run alembic upgrade heads && poetry run python scripts/post_deploy.py",
```

`upgrade heads` (plural) applies every head; with the single head enforced by CI it does the same as `upgrade head`. If the command fails, the deploy does not proceed.

The second command exists because Alembic runs each migration inside a transaction, and `CREATE INDEX CONCURRENTLY` cannot run inside one. Building an HNSW index normally takes a lock that blocks writes to the table; `CONCURRENTLY` avoids that. So the migration files for HNSW indexes are empty, and the indexes live in a list in `post_deploy.py`, each guarded by a check in `pg_indexes`:

<!--src content-queue-backend/scripts/post_deploy.py-->
```python
conn = psycopg.connect(
    dsn, autocommit=True
)  # CONCURRENTLY requires autocommit (no transaction)
```

The consequence is that the schema is defined in two places. A fresh database built only with `alembic upgrade heads` has no HNSW indexes. Also, the development database's `alembic_version` is `e7bda5920f1f`, two revisions behind the repository head `a7d3e9c15b42`, yet it has the HNSW indexes: they were applied by running the script by hand (inferred; the dev database was not modified).

### Connection pooling

<!--src content-queue-backend/app/core/database.py-->
```python
engine = create_engine(
    database_url,
    pool_size=3,
    max_overflow=2,
    pool_recycle=1800,
    pool_pre_ping=True,
```

A pool keeps open database connections for reuse, because opening one costs a network round trip and a Postgres process. Here each Python process keeps 3 and may open 2 more under load, 5 at most. A request that needs a sixth waits up to `pool_timeout=10` seconds and then fails with an error, instead of hanging for SQLAlchemy's 30-second default. `pool_pre_ping` checks a connection before use, and `pool_recycle=1800` replaces connections older than 30 minutes. The consequences:

- The API process serves at most 5 requests at the same time that are inside a database call. FastAPI runs synchronous endpoints in a thread pool, so more concurrent requests queue for a connection rather than for a thread.
- Each worker process also has its own pool of up to 5. Total connections are 5 times the number of processes. Postgres's default limit is 100 (`max_connections` on the development server; the production value was not checked).
- A slow request that holds a session open while it waits for an LLM call holds one of the five connections. The memory work (chapter 5.2) and `defer_heavy_columns` in `services/content.py` keep large columns out of list queries for related reasons.
- There is no PgBouncer. At more instances the sum of pools, not the load, is what reaches the Postgres limit first.

### Backups

The repository documents no backup or restore procedure, and an internal audit dated 2026-10-12 (not published) reached the same finding. Whether Railway-side backups are enabled was not verified there, and this guide did not check the live service either. Nothing here establishes an RPO (how much data can be lost) or an RTO (how long a restore takes); `docs/design/systems/distributed-systems-guide.md` proposes 24 hours and 4 hours as defensible targets that mean nothing until a restore has been timed.

## Design choices

| Choice | Alternatives | Why this one |
|---|---|---|
| One Postgres with pgvector for rows, text and vectors | A separate vector database; Elasticsearch for text | One transactional store: chunks and their article change together, and one deploy to run. See ADR-0001 in `docs/decisions/`. The limit is that vector search shares CPU and memory with everything else. |
| UUID primary keys generated in Python | Serial integers; UUIDs generated by `gen_random_uuid()` as a column default | Ids are unguessable in URLs and can be created before the insert. The column has no database default, so raw SQL inserts must supply the id (the scratch walkthrough had to). |
| Isolation by `user_id` in application code | Row-level security (RLS) policies | Simple and visible in each query. A missed filter is a data leak; see "What is weak". |
| Soft delete with a 7-day purge | Hard delete; an archive table | Gives an undo window. The cost is that every query must remember the filter (the table above shows three paths that do not). |
| Partial unique index for URLs | A full unique index; a separate `deleted` table | Lets a user re-save a URL they trashed. |
| Trigger-maintained `search_vector` | Generated column; computing in Python | Works whichever code path writes the row, including scripts. Recomputes the whole vector on each body change. |
| HNSW built outside Alembic | A normal migration | `CONCURRENTLY` avoids blocking writes during a build. The schema is split across two mechanisms. |
| Small pool (3 + 2) with a 10 s timeout | A larger pool; PgBouncer | Keeps total connections low on a small plan, and fails fast. Concurrency is capped at 5 per process. |
| Shared `tag_embeddings` | Per-user tags | Each label is embedded once for everyone. The table has no owner, so it reveals nothing about who uses a label, but it also cannot be deleted with a user. |

## How it fails

| Failure | What causes it | What happens | What was done |
|---|---|---|---|
| Duplicate saves | Two concurrent requests pass the duplicate check | Two items, double processing | The partial unique index; the database now rejects the second insert |
| Old rows not normalized | Rows saved before normalization was consistent | Duplicate detection missed them, so it fell back to scanning the library | Migration `a7d3e9c15b42` rewrote them and the scan was removed |
| Migration breaks the deploy | An error in `alembic upgrade`, or two heads | The pre-deploy command fails, so the deploy stops | CI single-head check; pre-deploy runs before traffic |
| Pool exhaustion | More than 5 simultaneous database calls in one process | Callers wait 10 s then get an error | Fail-fast timeout instead of 30 s |
| Trashed article still answers a question | `query_library` has no `deleted_at` filter | A deleted article's text can appear in an answer | Open |
| Orphans after hard delete | Entities, cluster id arrays | Stale entity rows and ids remain | Not handled |
| Lost data | No documented backup | Not recoverable by a documented procedure | Open |

## What is weak or missing

Ranked by how likely each is to matter.

1. **No backups or restore test in the repository.** Everything else on this list is recoverable if a restore works. Fix: enable a Railway backup policy, restore once into a scratch environment, time it, and write the numbers into `ARCHITECTURE.md`.
2. **Isolation depends on every query remembering `user_id`.** There is no Postgres row-level security. The internal audit of 2026-10-12 judged the content, highlight, list and public paths sound, and the text-to-SQL path is guarded by a parser. But `entity_mentions`, `entity_relations`, `tag_embeddings` and others rely on the same discipline. Fix: RLS policies keyed on a per-request setting, at the cost of setting that value on every connection.
3. **Soft delete is a convention, not a mechanism.** Three paths ignore it. Fix: a view or a repository helper that always adds the filter, or a global query filter in the ORM.
4. **The schema is split between Alembic and `post_deploy.py`.** A new engineer rebuilding from migrations alone gets no vector indexes. Fix: a CI step that runs both on an empty database and compares `pg_indexes` with a checked-in list.
5. **The pool is tiny and not load-tested.** No load test and no record of the production connection limit are in the repository.
6. **Unreferenced data accumulates.** Entities with no mentions, stale `article_count`, `reading_clusters` ids without foreign keys, and S3 objects for PDFs (account deletion calls `db.delete` and no code under `app/` deletes the stored objects).
7. **Unused indexes.** The IVFFlat index on `tag_embeddings` is 57 MB, half of that table. Whether queries use it was not measured here.

{% say %}
sed.i keeps everything in one Postgres database with the vector extension. A saved URL is one row in the content table; background jobs then add its passages with their vectors, its entities and mentions, and its tags. Most tables point at the user and cascade on delete. Deleting an article just sets a timestamp, and a daily job removes it a week later; most queries filter those out, but the text-to-SQL tool and the highlight and entity-graph code do not. A partial unique index on user and URL stops duplicates, a trigger keeps the full-text column current, and HNSW indexes serve vector search. Schema changes go through Alembic, run by Railway before each deploy, with the vector indexes built by a separate script because they need to be created concurrently. The weak points are that there is no documented backup, and that isolation between users relies on application code rather than the database.
{% endsay %}

## Check yourself

{% qa "A user trashes an article and saves the same URL again. Why does the database allow it, and what would break if the unique index were not partial?" %}
The unique index only covers rows where `deleted_at IS NULL`, so the trashed row is outside it and the new active row does not conflict. A plain unique index on `(user_id, original_url)` would reject the second save until the trashed row was purged seven days later.
{% endqa %}

{% qa "Why is the HNSW index not created inside an Alembic migration, and what is the cost of that decision?" %}
Alembic runs migrations in a transaction and `CREATE INDEX CONCURRENTLY`, which avoids blocking writes during the build, cannot run in one. The indexes are built by `post_deploy.py` instead. The cost is that the schema is defined in two places, so a database built from migrations alone lacks them.
{% endqa %}

{% qa "What does the trigger on content_items do, and why is it a trigger rather than a generated column?" %}
It rebuilds `search_vector` whenever the title, author, description, tags or body change, weighting each field. Generated columns need immutable expressions and `to_tsvector` is only stable, so Postgres would not accept it. A trigger also works for any code path that writes the row.
{% endqa %}

{% qa "The pool is 3 plus 2 with a 10 second timeout. What happens at the sixth simultaneous database call in one process, and what grows when you add a second worker?" %}
The sixth waits up to 10 seconds for a connection to be returned, then fails with a timeout error. Adding a worker adds its own pool of up to 5, so the total connection count is 5 times the number of processes, and the Postgres connection limit is reached by the sum, not by load.
{% endqa %}

{% qa "Name one place where a soft-deleted article can still show up, and say how you would fix it." %}
`query_library`: the schema shown to the model has no `deleted_at` column and the validator never requires a filter on it. Fix by requiring `deleted_at IS NULL` in the validator, or by letting the model query a view that already excludes trashed rows.
{% endqa %}

{% qa "Hard-deleting an article removes its chunks and mentions but leaves its entities. Why, and is it a bug?" %}
Entities belong to the user, not to one article, and other articles may mention them, so the foreign key from mentions to entities cascades only downward. Leaving them is correct while another article mentions them; the gap is that nothing removes or recounts entities that end up with no mentions.
{% endqa %}
